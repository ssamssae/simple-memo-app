## 0. 한 줄 요약

메모요의 데이터 구조(`List<Memo>` = id(uuid) + content + isFavorite + createdAt + updatedAt, SharedPreferences 단일 키)는 **레코드별 last-write-wins(LWW) 병합에 거의 이상적**이다. 다기기 동기화의 진짜 난점은 알고리즘이 아니라 (1) **삭제 처리(현재 tombstone 없음 → 스키마 갭)**, (2) **iCloud(Apple 전용) vs Drive(크로스플랫폼) 백엔드 분기**, (3) **1.0.7 이 못박은 "백그라운드 sync 금지" 비기능 박제와 "다기기 동기화" 메이저 목표 사이의 정면 충돌** 세 가지다. 본 노트는 이 셋을 surface 하고 단계적 경로를 제안한다.

## 1. 출발점: 현재 데이터 모델 (실측)

`lib/models/memo.dart` / `lib/services/memo_storage.dart` 기준:

```dart
class Memo {
  final String id;          // uuid v4 — 기기 간 충돌 없는 안정 키 ✅
  String content;
  bool isFavorite;
  final DateTime createdAt; // 불변
  DateTime updatedAt;       // 변경 시각 ✅
}
```

- 저장: `SharedPreferences` 의 단일 키 `'memos'` 에 전체 리스트를 JSON blob 으로 통째 encode/decode.
- 동기화 관점에서 **좋은 점**:
  - `id` 가 uuid v4 라 기기별 생성 메모가 충돌 없이 합쳐진다 (auto-increment 였으면 재앙).
  - `updatedAt` 가 이미 있어 레코드별 LWW 의 비교 축이 공짜로 존재.
  - 레코드 수가 적고(개인 메모) 페이로드가 작아 **full-blob 동기화도 현실적** — delta/CRDT 같은 무거운 엔진 불필요.
- 동기화 관점에서 **부족한 점 (스키마 갭)**:
  - **삭제 흔적이 없다.** 메모를 지우면 리스트에서 사라질 뿐 "삭제됨" 기록이 안 남는다. → A기기에서 지운 메모가 B기기 동기화 때 "B엔 있는데 A엔 없네 = 추가하자"로 **부활(resurrection)** 한다. 동기화의 1번 함정.
  - 기기 식별자(`deviceId`)·스키마 버전(`schemaVersion`) 없음.

## 2. 백엔드 후보 A — iCloud (Apple 전용)

### 2.1 세 가지 iCloud 저장 방식

| 방식 | 한도/특성 | 메모요 적합도 |
|------|-----------|---------------|
| **NSUbiquitousKeyValueStore** (KV) | 총 1MB / 1024 키. 자동 동기화, 로그인 UI 0 | 메모 수 많아지면 1MB 천장 위험. blob 1개로 넣으면 키는 1개지만 1MB 제한 그대로 |
| **CloudKit private DB** | 사실상 무제한(사용자 iCloud 용량), 레코드 단위 | 레코드별 동기화에 정석. 단 Flutter 바인딩 빈약 |
| **Document-based (ubiquity container 파일)** | iCloud Drive 안 앱 폴더에 파일. Files 앱 노출 가능 | 1.0.7 의 "단일 폴더 백업" 사고방식과 가장 유사 |

### 2.2 Flutter 패키지 현황 (2026-05 기준, 검증 필요)

- **`cloud_kit`** — CloudKit private DB 의 KV 래퍼. key/value 둘 다 String(객체는 JSON). `getAll()` 제공. iOS 전용.
- **`icloud_kv_storage`** — CloudKit 기반 KV, iOS+macOS 다기기 동기화. 현재 **String 만** 동기화.
- **`icloud_storage`** (별도, 문서형) — ubiquity container 파일 업/다운로드·삭제·진행률 stream. document-based 방식에 적합.

> ⚠️ 세 패키지 모두 메인테넌스/버전 편차 큼. 정식 spec 단계에서 pub.dev 최신 버전·이슈 트래커·iOS 26 호환 실측 필수. native CloudKit 을 MethodChannel 로 직접 부르는 선택지도 비교 대상.

### 2.3 함의

- iCloud 는 **로그인 UI 0** 가 최대 강점 — 사용자가 기기에 iCloud 켜놨으면 끝. CS 부담 최소화 철학과 정합.
- 단 **Apple 생태계 안에서만** (iPhone↔iPad↔Mac). Android 는 iCloud 접근 불가 — 크로스플랫폼 동기화엔 무력.

## 3. 백엔드 후보 B — Google Drive (크로스플랫폼)

### 3.1 두 가지 위치

- **`appDataFolder`** (숨김 앱 전용 폴더) — 사용자 Drive UI 에 안 보임. `drive.appdata` scope. 동기화 상태파일을 두기에 깔끔(사용자가 실수로 못 지움). 단 사용자가 "내 백업 어딨어" 눈으로 확인 불가 → 1.0.7 의 "항상 같은 자리에 보이게" 철학과 상충.
- **가시 "Memoyo" 폴더** (1.0.7 이 쓰는 방식) — `drive.file` scope, 사용자가 Drive 앱에서 직접 봄.

→ **동기화 상태 파일은 `appDataFolder`, 사용자 백업 스냅샷은 가시 Memoyo 폴더** 로 역할 분리하는 게 깔끔할 수 있음 (정식 spec 검토 포인트).

### 3.2 1.0.7 자산 재사용

1.0.7 이 이미 `google_sign_in` + `googleapis`(drive_v3) + `extension_google_sign_in_as_googleapis_auth` 인증·업로드·rotate 사슬을 깐다. 1.1.x 동기화는 이 위에 **pull(다운로드) + merge** 만 얹으면 됨 — Drive 백엔드는 증분 작업.

### 3.3 함의

- **iOS + Android 모두 커버** = 진짜 크로스플랫폼 동기화는 Drive 만 가능.
- 단 **첫 사용 시 Google 로그인 시트** 필요 (iCloud 의 zero-login 대비 마찰 1단계).

## 4. 핵심 충돌 #1 — 백엔드 분기 전략 (mesh-vote "둘 다" 의 실제 의미)

iCloud 와 Drive 는 대체재가 아니라 **커버 범위가 다른** 백엔드다.

| 사용자 시나리오 | iCloud | Drive |
|------------------|--------|-------|
| iPhone + iPad | ✅ (zero-login) | ✅ |
| iPhone + Android | ❌ | ✅ |
| Android only(2대) | ❌ | ✅ |

선택지:

- **(a) 플랫폼 네이티브 디폴트** — iOS 는 iCloud 디폴트, Android 는 Drive. 크로스플랫폼(아이폰+안드) 쓰는 사용자는 수동으로 Drive 선택. → iOS 사용자 마찰 최소(zero-login), 단 "iOS 는 iCloud, 안드는 Drive" 가 섞인 사용자는 동기화 안 됨(서로 다른 백엔드).
- **(b) Drive 단일** — 모두 Drive. 일관성·크로스플랫폼 보장, 단 iOS 사용자도 Google 로그인 강제(마찰 + "왜 구글 로그인?" CS).
- **(c) 사용자 선택** — 첫 진입에 "iCloud / Google Drive" 택1. → 유연하지만 선택지가 CS 부담(1.0.7 철학 "사용자가 어디로 보낼지 선택 안 함" 과 충돌) + 두 백엔드 코드·테스트 2배.

> mesh-vote "iCloud + Drive 둘 다 3:2" 는 (a) 또는 (c) 를 함의. 어느 쪽인지가 **정식 spec 의 1번 결정사항**. 본 노트 추천: **(a) 플랫폼 네이티브 디폴트**, 단 한 사용자 안에서 백엔드 혼재 시 "동기화 안 됨"을 명확히 안내. 메모요의 무료·CS최소 제약에서 (c) 의 백엔드 2종 동시 운영 비용은 과함.

## 5. 핵심 충돌 #2 — "백그라운드 sync 금지" 박제 vs "동기화" 메이저

1.0.7 spec §2 가 못박은 비기능 박제 (2026-05-18 spec 계승):

> "사용자가 명시적으로 버튼 누른 순간에만 데이터가 이동 (백그라운드 sync / 자동 백업 / 자동 복원 모두 없음)"

그런데 1.1.x 의 목표 자체가 "다기기 메모 동기화". **이 둘은 정면 충돌한다.** 동기화의 사용자 가치는 대부분 "알아서 맞춰져 있음"에서 나오는데, 박제는 그걸 금한다.

동기화 트리거 스펙트럼(마찰·자동화 순):

1. **수동 "지금 동기화" 버튼** — 1.0.7 철학과 완전 정합. 사용자가 누를 때만 pull+merge+push. 단 "다른 기기에서 쓴 게 자동으로 안 보임" → 동기화 기대와 어긋나는 사용자 불만 가능.
2. **앱 포그라운드 진입 시 자동 pull** (+ 변경 시 자동 push) — 앱 열 때마다 최신화. "백그라운드"는 아님(앱 active 일 때만). 박제의 문자적 위반은 아니나 "자동 데이터 이동" 정신엔 닿음.
3. **진짜 백그라운드 sync** (BGTaskScheduler / WorkManager) — 박제 정면 위반. 배터리·복잡도·CS 폭증. **메모요엔 과함, 추천 X.**

> 추천: **2번(포그라운드 진입 자동 pull + 변경 자동 push)** 이 "동기화답다"와 "CS 최소" 의 균형점. 단 **이는 1.0.7 의 박제를 1.1.x 에서 의도적으로 완화하는 결정**이라, 형님 명시 ack 필요. 박제를 못 풀면 1번(수동 동기화 버튼)으로 후퇴하되, 그건 "백업/복원의 1버튼화"에 가깝지 진정한 동기화는 아님을 명확히 해야 함.

## 6. 충돌 해결(conflict resolution) 설계

### 6.1 기본: 레코드별 LWW (updatedAt 기준)

- 같은 `id` 가 양쪽에 있으면 `updatedAt` 늦은 쪽 채택. 모델에 이미 있어 추가 비용 0.
- 다른 `id` 는 단순 union(합집합).

### 6.2 삭제 — tombstone 필요 (스키마 변경)

§1 의 부활 함정 해결책. 옵션:

- **(a) tombstone 필드 추가** — `Memo` 에 `bool isDeleted` + `DateTime? deletedAt` 추가. 삭제 = 리스트에서 제거가 아니라 `isDeleted=true` 마킹. 동기화는 tombstone 도 LWW 비교. 일정 기간(예: 30일) 후 tombstone GC.
  - 보너스: 1.0.7 메이저 묶음의 **(4) 휴지통 30일** 항목과 자연스럽게 합쳐짐 (휴지통 = 사실상 tombstone + 복원 UI). → 동기화 설계와 휴지통 설계를 **한 스키마로 묶는 게 효율적**.
- **(b) 삭제 ID 별도 리스트** — 본문과 분리된 `deletedIds` 셋. 단순하지만 GC·시각 비교 부실.

> 추천: **(a)**, 그리고 1.0.7 (4) 휴지통과 스키마 통합 검토. 동기화 때문에라도 tombstone 은 불가피하니, 휴지통 기능과 한 번에 설계하면 중복 작업 0.

### 6.3 엣지 케이스

- **편집 vs 삭제** (A는 수정, B는 삭제): tombstone LWW 로 `deletedAt` vs `updatedAt` 늦은 쪽. "지웠는데 살아남음" 가능 → 사용자 직관과 어긋날 수 있어 정책 명시 필요(보수적으론 "편집이 삭제를 이긴다" = 데이터 보존 우선, 1.0.7 §2 "메모 안 사라짐" 박제와 정합).
- **isFavorite 토글 충돌**: content 와 별개 필드라 필드별 LWW 가 이상적이나, 단순화하면 레코드 통째 LWW 로 충분(즐겨찾기 충돌은 저빈도·저영향).
- **content 동시 편집**: 메모요는 단일 사용자 다기기라 진짜 동시편집 빈도 낮음. 문자 단위 머지(CRDT) 과함 — 레코드 LWW 로 충분. "둘 다 살리기"가 필요하면 충돌 시 **분기 메모 생성**(양쪽 보존, "(충돌본)" 접미) 이 데이터 손실 0 의 안전판.
- **시계 오차(clock skew)**: 기기 시각 틀어지면 LWW 오판. 메모요 수준에선 허용오차로 두되, 정 신경 쓰면 동기화 페이로드에 서버측 시각 대신 논리적 카운터(per-device Lamport)까지 갈 수 있으나 **과함, 추천 X**.

## 7. 오프라인 정책

- **로컬(SharedPreferences)이 SoT.** 앱은 항상 로컬을 읽고 쓴다. 오프라인에서도 100% 동작(현재 그대로).
- 동기화 레이어는 로컬 ↔ 원격 스냅샷을 **조정(reconcile)** 하는 부가 레이어일 뿐, 로컬 동작 경로에 끼어들지 않음(오프라인 안정성 보존).
- 페이로드가 작으므로 **pending change queue 보다 full-snapshot diff 가 단순**: 원격 스냅샷 받아서 로컬과 §6 규칙으로 merge → 결과를 로컬에 쓰고 원격에 push. 마지막 동기화 시각만 들고 있으면 됨.
- 충돌 가능성을 더 줄이려면 원격 스냅샷에 `lastSyncedDeviceId` / `syncedAt` 메타를 둠.

## 8. 필요한 스키마 변경 요약 (정식 spec 입력)

1. `Memo` 에 `isDeleted` / `deletedAt` (tombstone) — §6.2. **1.0.7 (4) 휴지통과 통합 검토.**
2. (선택) `schemaVersion` 전역 필드 — 향후 마이그레이션 안전판.
3. (선택) 동기화 메타 파일 — Drive `appDataFolder` 또는 iCloud 에 `{ lastSyncedAt, deviceId }`.
4. `Memo.fromJson` 은 이미 누락 필드에 기본값을 주므로(현재 코드) **하위호환 안전** — 새 필드도 같은 패턴이면 구버전 데이터 무손실 로드 가능. ✅

## 9. 명시적으로 안 하는 것 (scope 가드, 정식 spec 에서 재확인)

- **실시간 협업 / 동시편집 / CRDT** — 단일 사용자 다기기 시나리오엔 과함.
- **자체 서버 / Firebase** — 무료앱·서버비 0 박제 위반. 사용자 본인 iCloud/Drive 만 씀.
- **종단간 암호화** — 1.0.7 §9 그대로(사용자 본인 클라우드라 노출 위험 작음). 채널 우려 들어오면 재검토.
- **3rd 클라우드(Dropbox 등)** — 분기 2개로 충분, 추가 시 CS 폭증.

## 10. 단계적 경로 제안 (정식 spec 의 골격 후보)

1. **선결정 (형님/본진)**: §4 백엔드 분기 전략 [(a)/(b)/(c)] + §5 동기화 트리거 [1/2/3] 두 가지를 먼저 못박는다. 나머지는 여기서 따라옴.
2. **스키마 선행**: tombstone(§6.2) 을 1.0.7 (4) 휴지통과 묶어 먼저 도입 (동기화 없이도 단독 가치 있음).

4. **iCloud 동기화 후속** (iOS 한정, zero-login UX). Flutter 패키지 실측 후 채택 vs MethodChannel 직접.
