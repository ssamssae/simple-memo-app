### 2.2 현 헬퍼 (`*ForTest` 메서드) 의 한계

이미 박혀있는 `*ForTest` 헬퍼:
- `obtainAuthClientForTest(GoogleSignIn gsi)` — GoogleSignIn 인자 받음 (DI 가능)
- `uploadJsonFileForTest(DriveApi api, ...)` — DriveApi 인자 받음
- `downloadBackupContentForTest(DriveApi api, ...)`
- `findMemoyoFolderForTest(DriveApi api)` / `ensureMemoyoFolderForTest`
- `listBackupsInFolderForTest(DriveApi api, ...)`
- `rotateForTest(DriveApi api, ...)`
- `downloadLatestForTest(DriveApi api)`
- `mapErrorForTest(Object e)` — 순수 함수

이들은 인자로 DriveApi/GSI 받지만 **퍼블릭 entrypoint** (`uploadBackup` / `listBackups` / `downloadBackup`) 는 인자 받지 X. widget 테스트가 entrypoint 를 거치므로 mock 갭.

### 2.3 widget 진입 path 의 mock 불가능 위치

```
MemoListScreen 위젯
  → 사용자 탭
  → memo_list_screen.dart 의 _onOverflowSelected('drive_backup')
  → DriveBackupService.uploadBackup(_memos)   ← entrypoint
  → static _signIn.signIn()                    ← ① 가로채기 가능 (channel mock)
  → static _signIn.authenticatedClient()       ← ② 가로채기 불가 (channel 외부 코드)
  → drive.DriveApi(authClient)                 ← ③ 가로채기 불가 (생성자)
  → api.files.create(...)                      ← ④ 가로채기 불가 (실 HTTP)
```

② 는 `extension_google_sign_in_as_googleapis_auth` 패키지 코드 — channel mock 만으로 누락된 OAuth2 token → http client 변환 단계 못 가로챔. ③ 은 그 결과로 만든 실 DriveApi.

## §3 옵션 (3안)

### §3.1 옵션 A — static setters DI 훅 (가장 surgical, 추천)

```dart
class DriveBackupService {
  static GoogleSignIn? _signInOverride;
  static drive.DriveApi? _apiOverride;
  static final _defaultSignIn = GoogleSignIn(
    serverClientId: '601847949978-...',
    scopes: _scopes,
  );

  // 테스트 전용. production 호출 X (analyzer hint 또는 assert).
  @visibleForTesting
  static void setSignInOverride(GoogleSignIn? gsi) {
    _signInOverride = gsi;
  }
  @visibleForTesting
  static void setApiOverride(drive.DriveApi? api) {
    _apiOverride = api;
  }

  static GoogleSignIn get _signIn => _signInOverride ?? _defaultSignIn;

  static Future<DriveBackupListResult> listBackups() async {
    final account = await _signIn.signIn();
    if (account == null) return ...PermissionDenied();
    final api = _apiOverride ?? await _buildApi();
    // ... 기존 흐름 ...
  }

  static Future<drive.DriveApi> _buildApi() async {
    final authClient = await _signIn.authenticatedClient();
    if (authClient == null) throw const DriveBackupDownloadAuthException();
    return drive.DriveApi(authClient);
  }
}
```

**테스트 사용 예**:
```dart

  when(() => gsi.signIn()).thenAnswer((_) async => _MockAccount());
  DriveBackupService.setSignInOverride(gsi);
  final api = _MockDriveApi();
  // ... when().thenAnswer() 설정 ...
  DriveBackupService.setApiOverride(api);

  DriveBackupService.setSignInOverride(null);
  DriveBackupService.setApiOverride(null);
});

  await tester.pumpWidget(const MaterialApp(home: MemoListScreen()));
  // ... 탭 ... pump ... expect ...

```

**장**:
- 코드 변경 최소 — `_signInOverride` / `_apiOverride` 2 static field + 2 setter + 1 getter 변경. 기존 caller 0건 변경
- 1.0.8 휴지통/검색 코드와 충돌 0 — 서비스 internal change
- production 동작 동일 (override null 디폴트)
- `@visibleForTesting` 어노테이션으로 production 호출 = analyzer warning
- tear-down 누락 = global state leak risk (setUp/tearDown pair 강제)

**단**:
- static state — 병렬 테스트에서 race 발생 가능 (Dart 테스트는 디폴트 single-threaded 라 큰 risk X)
- `@visibleForTesting` 가 정책 strong 하진 X — production 코드가 setter 호출 가능 (소스 리뷰로 catch)
- 의존성 그래프가 명시적이지 않음 — "이 메서드가 GoogleSignIn 을 쓴다" 가 시그니처에 안 나옴

## §4 추천 + 사유

**추천**: **옵션 A** (static setters DI 훅, `@visibleForTesting`).

### 4.1 사유

- **surgical**: 2 static field + 2 setter + 1 getter + `_signIn` 참조 변경 (1줄) + `_apiOverride` 분기 (각 entrypoint 의 DriveApi 생성 라인). 영향 범위 = `drive_backup_service.dart` 단일 파일
- **1.0.8 묶음과 충돌 0**: 휴지통 (데이터 모델 + 새 화면) + 검색 (AppBar UX + SearchService) 코드 영역 영구 분리 — drive_backup_service.dart 한 파일만 건드림
- **caller 변경 0**: `memo_list_screen.dart` 의 모든 `DriveBackupService.uploadBackup(...)` 호출 그대로 — production 동작 동일
- **production 안전**: override 디폴트 `null` → `_defaultSignIn` / 실 DriveApi 생성 chain. production 코드가 setter 호출 X (`@visibleForTesting` analyzer + lint)
- **테스트 폭발**: 사이클 #9 의 (b) 6 widget 시나리오 + 향후 휴지통 spec §6 (Drive 백업 호환) + 검색 spec §4 (휴지통 검색) 등 자동화 가능

### 4.2 옵션 B/C 비추 사유

- 옵션 B 의 caller 마이그 = 1.0.8 묶음 (휴지통+검색) 진행 중 conflict 폭발 risk. 단일 사용자 단일 앱이라 DI 깨끗함 가치 < 마이그 비용
- 옵션 C 의 DI 프레임워크 도입 = 메모요 scope 명백히 초과. 1.0.x 동안 미루고 1.1.x 다기기 sync 진입 시 재평가

### 4.3 1.0.9+ 마이그 path

옵션 A → 옵션 B 마이그가 future-proof:
- 1.0.8 = 옵션 A 박음 → 자동화 폭발
- 1.0.9~1.1.x = 옵션 B 로 마이그 (다기기 sync / 새 서비스 추가하며 자연스러운 정리)
- 1.2.x+ = 옵션 C 도입 검토 (서비스 5+ 개 + DI 깨끗함 가치 > 마이그 비용 시)

- DriveApi mock 깊이 = 충분히 mock 시 widget 시나리오 = 사실상 service-level 테스트 위젯 wrapper. ROI 평가 별도
