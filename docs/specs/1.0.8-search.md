## §1 동기 + 사용자 시나리오

### 1.1 메모 N건 시 검색 갭

현재 (1.0.7) 메모 리스트 = 단순 ListView (즐겨찾기 그룹 + 일반 그룹). 메모 N건:
- N ≤ 30: 스크롤 한눈에 OK
- N ≈ 100: 스크롤 부담 + "그 메모 어디 있더라" 시작
- N ≥ 200: 검색 없이 못 찾음 → 사용자 신뢰 추락

iOS Notes / Google Keep / Apple Notes / Evernote 모두 디폴트 검색 — 메모요만 없으면 N ≥ 50 사용자 학습 부담.

### 1.2 사용자 시나리오 (dogfood)

**시나리오 A — "그때 그 책 메모 어디 있더라"**
- 강대종 dogfood: 메모요에 책 인용 + 일 메모 + 아이디어 메모 섞임 (현재 약 150건)
- "그 책 이름이 뭐였더라" 떠올림 → 검색 "Karpathy" → 즉시 매칭 1건
- **현재 (1.0.7)**: 스크롤 + 본문 펼침 반복 — 발견 못 할 가능성
- **1.0.8 with 검색**: 검색바 → 즉시

**시나리오 B — "비슷한 메모 묶음 보고 싶다"**
- "안전망" 키워드로 검색 → 1.0.7 안전망 / 1.0.8 안전망 / 백업 안전망 등 묶음 노출
- 매치 부분 노란색 highlight 로 시각 분류 가능

**시나리오 C — "삭제한 메모도 검색"**
- 휴지통 안에 어제 지운 "그 메모" — 일반 검색에서 안 잡힘
- 휴지통 안에 들어가서 휴지통 전용 검색 별 옵션 (§4)

### 1.3 안 만들면 잃는 것

- 메모 100건 넘어가면 스크롤 한계 → 새 메모 작성 빈도 감소 (사용자 = "이거 어차피 못 찾을 텐데" 패턴)
- iOS Notes / Google Keep 대비 명백한 학습 부담 — 디폴트 기능 부재
- 본인 dogfood 가 메모 200건 넘어가는 시점이 결정 변수 (현재 약 150)

## §2 데이터 모델 + 인덱싱

### 2.1 검색 대상 필드

| 필드 | 가중치 | 비고 |
|---|---|---|
| `Memo.firstLine` (제목 = 첫 줄) | 높음 | 제목 매치 = 사용자 의도 직접 |
| `Memo.content` (본문 전체) | 중간 | substring 매치 |
| `Memo.isFavorite` | 필터 옵션 | 검색 결과 안에서 즐겨찾기 우선 정렬 |
| `Memo.tags` (1.0.8 §2 묶음 시) | 높음 | 1.0.8 검색 spec 본인은 tag X 가정. tag 묶음 별 spec |

### 2.2 인덱싱 옵션

#### 옵션 A: in-memory linear scan (추천)
```dart
class SearchService {
  static List<Memo> search(List<Memo> memos, String query) {
    if (query.isEmpty) return memos;
    final q = query.toLowerCase();
    return memos.where((m) {
      return m.firstLine.toLowerCase().contains(q) ||
             m.content.toLowerCase().contains(q);
    }).toList();
  }
}
```

- **장**: 단순. 인덱싱 0 — 메모 갱신/추가/삭제 시 동기화 비용 0
- **장**: 메모 ≤ 500건 까지 60fps 유지 (linear scan O(N × M), M = 평균 본문 길이)
- **장**: 마이그레이션 0
- **단**: 메모 1000건 + 본문 평균 1KB = 1MB 스캔 × 입력 keystroke → 디바운스 필수 (300ms)
- **단**: 한글 자소 분리 X — `'ㄱ'` 입력 시 `'가'` 안 잡힘 (디폴트 substring)

#### 옵션 B: SharedPreferences 인덱스 (비추)
- 별 key `'search_index'` 에 token → memo id 역인덱스 박음
- 인덱스 동기화 비용 (모든 메모 갱신 시 인덱스 재계산) > 검색 비용 절감
- 메모 ≤ 500건 단계에서 옵션 A 가 동일 결과

#### 옵션 C: SQLite FTS5 마이그레이션 (비추, 1.0.9+ 후보)
- SharedPreferences → SQLite 전면 마이그
- FTS5 가상 테이블 + 한글 자소 토크나이저 = 검색 성능 폭발
- **하지만**: 1.0.8 scope 크게 초과. 데이터 이전 + 영속 layer 전면 재작성. 검색 외 기능에도 영향
- 1.0.9 + 메모 1000건 + 한글 자소 분리 요구가 명확해진 시점에 진입

**추천**: **옵션 A**. 1.0.8 디폴트, 1.0.9 부터 사용자 1000건 + 한글 자소 요구 모니터링 → 옵션 C 진입 판단.

### 2.3 매칭 알고리즘 세부

- **대소문자**: case-insensitive (영어). `toLowerCase()`
- **공백**: 트림 + 다중 공백 단일화 후 substring (예: `"a  b"` → `"a b"`)
- **한글 자소**: 디폴트 X. `'ㄱ'` 검색 = `'가'` 안 잡힘. 사용자 명시적 요구 시 1.0.9 추가
- **정규식**: X. 1.0.9 후보 (power user)
- **빈 쿼리**: 전체 메모 반환 = 디폴트 목록 그대로
- **공백만**: 빈 쿼리와 동일 (전체 반환)

### 2.4 디바운스

- 입력 keystroke 마다 search 호출 X. 디폴트 디바운스 = **300ms**
- 사용자 타자 평균 = 150~200 wpm = keystroke 간격 ≈ 80ms. 300ms 디바운스 = 사용자 멈춤 후 300ms 에 한 번 search
- 메모 500건 + 본문 1KB linear scan = ~ 5ms. 60fps 윈도우 16ms 안에 충분 — but 디바운스가 더 중요한 이유는 사용자 visual 부담 (결과 깜빡임) 줄임

## §4 휴지통과의 관계

### 4.1 검색 대상 — 활성 vs 휴지통

**옵션 A (추천)**: 검색 = **활성 메모만**. 휴지통 안에 들어가서 별 휴지통 검색 진입 가능 (옵션 B 와 동시)
- 휴지통 spec [[1.0.8-trash-30day.md]] §5 의 IS NULL 필터 일관성
- 사용자 직관: 검색 = "내 메모 찾기" = 살아있는 메모
- 휴지통 검색 = 휴지통 화면 내부 별 검색바 (오버라이드 동선)

**옵션 B**: 검색 = 활성 + 휴지통 모두. 결과 카드에 "휴지통" 배지 표시
- 휴지통 메모도 한 화면에 — 복원 동선 짧음
- 휴지통 spec §5 의 일반 필터링 일관성 깨짐 — 검색 따로 룰 적용

**옵션 C**: 검색 = 활성만, 휴지통 검색 미지원 (1.0.9 후보)
- 1.0.8 scope 최소화
- 휴지통 사용 빈도 낮은 가정 → 휴지통 안에서 스크롤로 충분

**추천**: **A**. 검색 = 활성만 + 휴지통 화면 내부 별 검색바 = 두 컨텍스트 분리 명확. 일관성 + 학습 부담 0.

### 4.2 휴지통 spec 과의 코드 호환성

- 휴지통 spec §5 의 `MemoStorage.loadMemos` (활성만) + `loadTrash` (휴지통만) 분리 그대로
- `SearchService.search(memos, query)` 가 받는 `memos` 인자 = 호출 컨텍스트 결정 (메모 리스트 화면 = loadMemos / 휴지통 화면 = loadTrash)
- 검색 서비스는 휴지통 인지 X — pure function 으로 독립

### 4.3 1.0.8 묶음 결정 (휴지통과의 trade-off)

| 묶음 | scope | 가치 | risk |
|---|---|---|---|
| 휴지통 단독 | 작음 | 데이터 안전망 완성 (시급) | 검색은 1.0.9 carry |
| 휴지통 + 검색 | 중간 | 두 핵심 갭 동시 메꿈 | scope 분산 risk |
| 검색 단독 | 작음 | 메모 N건 사용성 | 휴지통 carry — 1.0.7 안전망 미완성 carry over |

**추천**: 형님 ack 후 결정. 본 spec 작성자 선호 = **휴지통 + 검색 묶음** (두 데이터 모델 변경이 독립적 + 사용자 가치 즉시).

## §5 회귀 안전망 (구현 PR 시 동반 위젯/단위 테스트)

### 5.1 서비스 단위 — SearchService.search

- 빈 쿼리 → 전체 메모 반환
- 공백 only 쿼리 → 전체 반환
- 제목 매치 1건 → 정확히 1건 반환
- 본문 매치 1건 → 1건 반환
- 제목 + 본문 매치 동시 → 1건 (중복 X)
- 대소문자 무관 (`'KARPATHY'` 검색 = `'karpathy'` 매치)
- 다중 공백 트림 (`"a  b"` 검색 = `"a b"` 매치)
- 한글 자소 분리 X 명시적 contract — `'ㄱ'` 검색 시 `'가'` 매치 X (1.0.9 후보 forcing function)

### 5.2 위젯 시나리오

- **검색 진입**: AppBar 🔍 → AppBar morph 으로 TextField 노출 + 뒤로가기 버튼
- **검색 입력**: TextField "Karpathy" → 디바운스 300ms 후 결과 1건 표시
- **하이라이트**: 결과 카드에 매치 부분 amber 배경 (RichText `style: TextStyle(backgroundColor: ...)` 검증)
- **빈 결과**: TextField "asdjkfh" → 빈 결과 empty state
- **결과 ranking**: 즐겨찾기 1건 + 일반 1건 둘 다 매치 → 즐겨찾기 1번째
- **결과 ranking**: 제목 매치 + 본문 매치 → 제목 매치 1번째
- **검색 모드 이탈**: 뒤로가기 → AppBar 원복 + 전체 목록 복귀
- **검색 결과 탭**: 결과 카드 탭 → 편집 화면 진입 (기존 라우팅 유지)

### 5.3 1.0.7 회귀 보호

- 검색 모드 이탈 후 ReorderableListView 동작 정상 (사이클 #6 reorder 회귀 안전망과 묶음)
- 검색 진입 ↔ 이탈 트랜지션이 ScrollPosition 깨뜨리지 않음 (목록 스크롤 위치 보존)
